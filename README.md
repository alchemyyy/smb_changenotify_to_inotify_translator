# SMB ChangeNotify to inotify Translator

Bridges the gap between network filesystem change notifications and Linux inotify. 

Uses a Sambda share to listen for SMB2 CHANGE_NOTIFY events, then translates them into inotify events.

This program is completely independent of the actual filesystem mount you have. You can continue running NFS on linux for the actual data share. All this requires is read-access level SMB to the same data.

Example: If using TrueNAS, set up a read-only SMB share to the same place as your existing NFS share.

## The problem

Linux inotify doesn't work on NFS or SMB mounts. When a file changes on the server, local applications watching the mount with inotify see nothing. Most media servers fall back to periodic rescanning, which is slow and wasteful.

## How it works

Two components:

### 1. Kernel module (`inotify_trigger`)

A small GPL kernel module that exposes `/proc/inotify_trigger`. Writing `<event_mask> <path>` to it calls the kernel's `fsnotify()` directly on the resolved inode. This fires real inotify events — indistinguishable from ones generated by actual filesystem operations — without touching the filesystem at all. No writes to disk, no writes to the network, no feedback loops.

```
echo "0x2 /media/music/song.flac" > /proc/inotify_trigger  # IN_MODIFY
```

### 2. Python translator script

Connects to the SMB server using the SMB2 CHANGE_NOTIFY protocol (the same mechanism Windows uses for real-time file notifications). When changes are detected, it writes the corresponding event to `/proc/inotify_trigger`. The kernel module injects the event, and any application watching that path with inotify sees it immediately.

```
SMB server detects file change
        ↓
SMB2 CHANGE_NOTIFY fires
        ↓
Python script receives notification
        ↓
Writes to /proc/inotify_trigger
        ↓
Kernel module calls fsnotify() on the inode
        ↓
Jellyfin/Navidrome/Plex inotify watch fires
```

Zero filesystem operations in the entire chain. The data mount (NFS, SMB, whatever) is never touched.

## Requirements

- Linux >= 5.14 (for the kernel module)
- Python 3
- Root access (for the kernel module and systemd service)
- DKMS, build-essential, and kernel headers (installed automatically by `--install`)

## Install

1. Copy this directory to the target machine.

2. Edit the config (generated on first run) or create `smb_changenotify_to_inotify_translator_config.json`:

```json
{
    "smb_server": "192.168.1.50",
    "smb_port": 445,
    "smb_username": "user",
    "smb_password": "password",
    "watches": [
        {
            "share": "media",
            "remote_path": "Video",
            "local_path": "/shares/video"
        },
        {
            "share": "media",
            "remote_path": "Music",
            "local_path": "/shares/music"
        }
    ]
}
```

- `share` — the SMB share name
- `remote_path` — subdirectory within the share to watch (the SMB2 CHANGE_NOTIFY target)
- `local_path` — where the share is mounted locally (where inotify events are injected)

3. Install everything:

```bash
sudo python3 smb_changenotify_to_inotify_translator.py --install
```

This does three things:
- Installs the `smbprotocol` Python package
- Builds and installs the `inotify_trigger` kernel module via DKMS (survives kernel updates)
- Creates and enables a systemd service

## Usage

```
--install             Full install (pip deps + kernel module + systemd service)
--uninstall           Full uninstall (stop service + remove module + cleanup)
--reinstall-module    Rebuild just the kernel module
--test                Test SMB connection (lists directory contents)
```

Or run directly:

```bash
sudo python3 smb_changenotify_to_inotify_translator.py
```

## inotify Event Verification

A verification script is included to confirm events are arriving:

```bash
python3 verify_inotify.py
```

This watches the configured `local_path` directories with `inotifywait` and prints events as they arrive. Make a change on the SMB server and you should see it appear.

**NOTE:** inotify is shallow! you're only going to see events if you modify files/folders in your root share directories (what this verification script defaults to. it pulls them from the config file.) Apps that use the inotify system are setting hundreds/thousands of watches!

## Uninstall

```bash
sudo python3 smb_changenotify_to_inotify_translator.py --uninstall
```

Stops the service, removes the systemd unit, unloads the kernel module, and removes the DKMS entry.

## Notes

- The SMB connection for CHANGE_NOTIFY is completely independent from how you mount the share. You can mount via NFS and still get SMB change notifications — the script opens its own SMB session just for the notification subscription.
- The kernel module auto-rebuilds on kernel updates via DKMS.
- SMB2 CHANGE_NOTIFY watches are recursive — a single watch on a directory covers the entire subtree.
- Duplicate events from SMB burst-firing are suppressed with a 2-second cooldown per (action, path) pair.
- The correct inotify event type is injected (IN_CREATE, IN_DELETE, IN_MODIFY, IN_MOVED_FROM, IN_MOVED_TO) rather than a generic IN_ATTRIB.
